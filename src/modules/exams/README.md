# Module `exams`

Multiple-choice exams on a page (documento-maestro §3.3, §6.1, §7.2, §7.5):
questions written by hand or generated by AI, exam sessions with
deterministic correction, retakes with reformulated variants when a page
scores below 70 %, and AI feedback. Built in Phase 5 (§13) under ODD; the
feature document is `odd/tasks/phase-5-exams.md` and the decisions are
recorded in `docs/adr/0006-examenes-y-repeticion-con-variantes.md`
(documento-maestro 1.4.0).

## Map

| Layer | Where | What |
|---|---|---|
| Domain | `domain/` | Pure rules: questions and lineages, sessions, scoring, composition, SM-2 quality, feedback policy; repository and hub-reader ports. |
| Use cases | `application/` | Manual questions, AI generation, session (start, answer, finish, read), retake, feedback, review notice, hub. In-memory fakes and shared contracts in `application/testing/`. |
| Adapters | `infrastructure/` | Drizzle repositories, unit-of-work adapters (one transaction each) and the hub reader. |
| Server Actions | `actions.ts`, `session-actions.ts`, `retake-actions.ts`, `feedback-actions.ts`, `hub-actions.ts` | The only UI entry points; exported through `index.ts`. |
| AI prompts | `src/modules/ai` | `generate_exam_questions/v1`, `generate_exam_variants/v1`, `session_feedback/v2` (exams never import the AI SDK). |
| Screens | `src/app/(app)/exams/` | Hub, notebook view, start, player, results, questions. |

## Server Actions

All of them check the session first, validate input with Zod and never
throw (`action-support.ts`); errors come back as `{ code, message }`.

| File | Actions |
|---|---|
| `actions.ts` | `listExamQuestionsAction`, `editExamQuestionAction`, `retireExamQuestionAction`, `generateExamQuestionsAction` |
| `session-actions.ts` | `getExamStartAction`, `startExamSessionAction`, `getExamSessionAction`, `answerExamQuestionAction`, `finishExamSessionAction`, `getExamResultsAction` |
| `retake-actions.ts` | `startExamRetakeAction` |
| `feedback-actions.ts` | `requestExamFeedbackAction`, `getExamReviewNoticeAction` |
| `hub-actions.ts` | `listExamHubAction` |

Analytics is best-effort (`trackSafely`: a rejected event goes to Sentry and
is dropped), and a feedback read failure in `getExamResultsAction` returns
`feedback: null` instead of hiding the score.

## Manual questions (T4)

- `createExamQuestion` checks the page is the owner's (`PAGE_NOT_FOUND`),
  validates with `newExamQuestion` and saves the root together with its
  `StudyItem(kind = "exam_question", sourceId = rootId)` in one
  `ExamUnitOfWork` run, so `recordExamReviews` always finds the item. No
  Server Action calls it since Phase 8 H13; it stays because the database
  tests (unit of work, session, retake) and `actions.test.ts` seed questions
  through it, and `editExamQuestion` reuses its `ExamQuestionContent`.
- `editExamQuestion` edits in place (same id, root, origin); a retired
  question answers `EXAMS_QUESTION_RETIRED`, another owner's
  `EXAMS_QUESTION_NOT_FOUND`.
- `retireExamQuestion` retires (never deletes) and, when the root's lineage
  has no active question left, suspends the root's item in the same run.
  Idempotent: a second call keeps the first `retiredAt`.
- `listPageExamQuestions` lists the page's active questions, oldest first.
- `runExamWork` turns an err Result into a rollback (a unit of work only
  rolls back on a throw). `DrizzleExamUnitOfWork` runs one transaction with
  the question repository and study-engine's `createStudyItemRepository`.
- `action-support.ts` duplicates the small flashcards boundary helpers
  (session, Zod parse, never-throw) with `EXAMS_*` codes: `src/shared`
  cannot depend on `identity`, and modules only meet through their index.

## AI generation (T5)

- `requestExamGeneration({ pageId, count })` mirrors flashcards'
  `requestGeneration`: count in [10, 30] (default 10,
  `EXAMS_INVALID_QUESTION_COUNT`), page owned (`PAGE_NOT_FOUND`) and not
  blank (`AI_PAGE_EMPTY`) are checked BEFORE `limiter.check`, which
  consumes ONE unit per request; a provider failure after the check keeps
  the unit consumed, as in flashcards.
- Incremental (Phase 6 T5c): only the paragraphs exams has not used on the
  page yet (new or edited, by fingerprint in `generation_fingerprints`) are
  sent; their fingerprints are stored with the questions. Nothing new
  answers `EXAMS_NO_NEW_CONTENT` before the limiter (no AI call, no unit); a
  page generated before T5c sends every paragraph once.
- Prompt `generate_exam_questions/v1` (ai module) receives the truncated
  page text, the count and the page's active questions (`[concept] stem`,
  last 60) so the model avoids duplicates.
- Batching: at most `EXAM_GENERATION_BATCH_SIZE` (15) questions per model
  call, split evenly (25 → 13 + 12); later calls also list the stems
  accepted from earlier ones. All calls finish before anything is written.
- Each question goes through `newExamQuestion(origin "ai", generationId of
  its call)`; invalid ones, stems equal (`normalizeWording`) to an active or
  already accepted stem, and extras beyond a call's count are skipped and
  counted. The valid roots and their study items are written in ONE
  `runExamWork`, which re-reads the active stems first (a manual question
  may land during the calls). Nothing usable → `AI_GENERATION_FAILED`,
  nothing stored.
- The fake provider (`AI_PROVIDER_MODE=fake`) reads the prompt and returns
  exactly `count` distinct questions whose numbered stems skip the listed
  existing ones.

## Exam session (T6)

- `startExamSession(pageId, N ∈ [10, 30])`: refuses a pending retake
  (`EXAMS_RETAKE_PENDING`, T7 reformulates the failed questions); resumes
  the page's open normal session as it is (its N and questions) instead of
  opening a second one; otherwise composes the exam (`composeExam`, < 10
  roots → `EXAMS_NOT_ENOUGH_QUESTIONS`) and stores the session. Starts of
  one page are serialized with a transaction-scoped advisory lock.
- The composed list is stored on the session (`exam_sessions.question_ids`,
  ordered ids, migration 0011, CHECK: a JSON array of 1 to `requested_count`
  ids). `composeNormalExam` runs once, at the start: questions shown at that
  instant (`listShownAt`, latest wording per root), earlier answers (least
  recently seen), the roots' due dates and failed roots. Answering,
  finishing and reading an open or finished session use the stored list
  only (`loadSessionQuestions`), so later changes to the page's questions
  or study items never move an open exam. T7 retakes store their variant
  ids the same way.
- `answerExamQuestion` locks the session row, checks the question is one of
  the session's stored ids and unanswered, grades it and returns the correct option
  and explanation (the player reveals each answer).
- `completeExamSession`, one transaction: lock the session `FOR UPDATE`,
  refuse a finished one (`EXAMS_SESSION_FINISHED`) or unanswered questions
  (`EXAMS_SESSION_INCOMPLETE`: an exam ends when all its questions are
  answered, so score = correct / total counts every question), derive the
  result (`finishExamSession`), upsert `ExamPageState` (`scoreExam`) and
  record every answer with `recordExamReviews` (a savepoint of the same
  transaction). Any failure rolls all of it back.

## Retake (T7)

- `startExamRetake({ pageId, requestedCount })`, in this order:
  1. Page not the owner's → `PAGE_NOT_FOUND`; N outside [10, 30] →
     `EXAMS_INVALID_QUESTION_COUNT`; no pending retake →
     `EXAMS_NO_RETAKE_PENDING`. The page's open retake is resumed
     (`findOpenRetakeByPage`) with no AI call.
  2. Plan: the failed roots of the last failed exam that still have an
     active question. None left → the pending retake is cleared under the
     page lock and `{ kind: "cleared" }` is returned (the page holds a
     normal exam again).
  3. Dry run: `composeRetake` with the current candidates and one
     placeholder per failed root. A retake that cannot be built (fewer
     than 10 roots, or N below the live failed roots) is refused here,
     before any AI call or limit read.
  4. A failed root with an active, unshown variant reuses it. The others go
     to `generate_exam_variants/v1` (at most 15 roots per call) after a
     `limiter.peek`; each variant is checked with `newVariant` against the
     root's whole lineage. Provider failure, unusable answer, missing root
     or repeated wording → `EXAMS_RETAKE_VARIANT_MISSING`, nothing stored.
  5. One transaction: page lock, re-plan (must match), `lockLineage` per
     root in id order, store the variants (`ai_variant`, `variant_of` = the
     wording shown in the failed exam), retire the replaced wordings,
     `composeRetake` and create the session with its `questionIds`.
  6. `limiter.check` consumes ONE unit only after that commit and only if
     the AI was called.
- `getExamPageOverview.failedRootCount` counts the same live failed roots
  the planner retakes (parity test in `start-exam-retake.test.ts`).

## Feedback and review before retaking (T8)

- `requestExamFeedback(sessionId)`: finished, owned sessions only
  (`EXAMS_FEEDBACK_SESSION_OPEN`). Policy via `decideFeedback`: a failed
  exam, the first pass and a failure after a pass get new feedback; a pass
  after an earlier pass returns that pass's stored row with `reused: true`,
  with no AI call and no row of its own (a chain of passes carries the last
  generated feedback forward). Generation mirrors flashcards: one
  `session_feedback` row per exam session (`session_kind = exam`) claimed
  once, stale pending rows reclaimed, settled only while pending, 25 s AI
  timeout, every failure stored as `failed` and returned as ok; the daily
  limit is only peeked. Prompt `session_feedback/v2`: failed questions
  (concept, stem, chosen and correct option, explanation; capped) plus the
  page text cut to `AI_PAGE_TOKEN_CAP`. `readExamFeedback` is the read-only
  variant the results view uses.
- `getExamReviewNotice(pageId)`: while a retake is pending, the current
  concepts of the failed roots (latest active wording); null otherwise or
  when every failed root was retired.

## Exams hub (T9)

- `ExamHubReader.listExamPages(ownerId)`: one row per page holding at least
  one active question (pages and notebooks not archived), ordered by
  notebook title then page title: active roots, finished sessions
  (retakes included), the latest finished session (`finishedAt`, `total`,
  `correct`, `passed`) and `retakePending`. The Drizzle reader runs two
  owner-wide queries (grouped questions; `DISTINCT ON` latest session with
  a window count), never one per page. Shared contract
  `application/testing/exam-hub-reader.contract.ts` (fake + `pnpm test:db`).
- `listExamHub` adds the whole-percent last score (rounded down, as on the
  results screen) and `dueToday`, the page's
  exam questions due today from scheduling's "Repasos de hoy"
  (`createSchedulingServerApi().listDueToday(ownerId, { timeZone })`,
  `due.exam_question`; reviews are due per local day of the profile's zone,
  user decision 2026-10-18). A
  failing due list degrades to `dueToday: null` (reported to Sentry), never
  hiding the hub.
- `failedDueNow` drives the retake banner copy: whether a failed root of
  the last exam has its item due today (study-engine `listDue` with the
  start of the owner's next local day as the bound, filtered to
  those roots through the `ExamDueCounts` port, built in `hub-actions.ts`);
  `null` when unreadable, and the banner falls back to neutral copy.
- The hub's header offers only "Crear examen" (Phase 6 T5b): pick a
  notebook and a page, then generate the questions with AI or write them on
  the page's `/preguntas` screen; the former "Nuevo examen" quick start was
  removed.

## Domain

- `exam-question.ts`: `ExamQuestion` (4 distinct options, one correct index,
  `concept`, lineage `rootId`/`variantOf`, origin `ai | manual | ai_variant`).
  `newExamQuestion` creates an original (its own root), `newVariant` the AI
  reformulation of a retake (same root and concept, never any earlier wording
  of the root's lineage — the caller passes that lineage; wordings compare
  ignoring case, spaces, `¿ ¡` and trailing punctuation),
  `editExamQuestion` edits in place keeping the root, `retireExamQuestion`
  retires it. A retired question cannot be edited, varied or retired again.
- `exam-session.ts`: `ExamSession`, `ExamAnswer` (`gradeExamAnswer` corrects
  deterministically), `ExamPageState` and the constants `EXAM_MIN_QUESTIONS`
  (10), `EXAM_MAX_QUESTIONS` (30), `EXAM_DEFAULT_QUESTIONS` (10) and
  `EXAM_PASS_THRESHOLD` (0.70). `finishExamSession` derives total, correct,
  score and passed from the session's answers (`tallyAnswers`: one answer per
  question and per root, none from another session, at most N) and refuses a
  finish before the start or a second finish. `examSessionDurationMs` derives
  the time shown on the results screen (the only place a time metric is
  shown).
- `scoring.ts`: `scoreExam` — pass iff score ≥ 0.70, decided with integer
  arithmetic (`isPassingScore`); duplicate answers are refused
  (`EXAMS_DUPLICATE_ANSWER`). A failure leaves a retake pending with the failed roots and
  keeps the last pass; a pass clears it and records the session.
- `composition.ts`: `composeExam` orders roots failed last time first, then
  due roots (due before `dueBefore`, the start of the owner's next local
  day, oldest first), then least recently seen (never seen first), one
  question per root, ties broken by id. `composeRetake` puts one fresh
  variant per failed root first, then the rest in the same order.
- `exam-quality.ts`: `examQualityFor` — wrong → review with q = 1 always;
  correct → q = 4 only if the root's item was due, otherwise SM-2 is skipped.
- `feedback-policy.ts`: `decideFeedback` — generate on a failed attempt and on
  the first pass; on a later pass reuse the stored feedback of the most recent
  earlier pass, or generate if that pass has none.

## Decisions

- **Not enough questions.** `composeExam` and `composeRetake` refuse a page
  with fewer than 10 active roots (`EXAMS_NOT_ENOUGH_QUESTIONS`) instead of
  starting a shorter exam; the UI asks the student to add or generate
  questions. With 10 or more roots an exam holds `min(N, roots)` questions.
- **Retake size.** A retake refuses an N below the number of failed roots
  (`EXAMS_INVALID_QUESTION_COUNT`), so every failed concept is always
  retaken; the UI should offer `max(10, failed roots)` as the minimum.
- **Blocked retake.** A failed root without a fresh variant, or whose variant
  is a question already shown, blocks the retake
  (`EXAMS_RETAKE_VARIANT_MISSING`). No earlier wording of the root is ever
  reused: `newVariant` refuses one (`EXAMS_VARIANT_SAME_WORDING`).

## Persistence

Tables `exam_questions`, `exam_sessions`, `exam_answers` and
`exam_page_state` (RLS on, no policies: only the server connection reaches
them). CHECKs mirror the domain: 4 options, correct index 0–3, an original is
its own root and only a variant has `variant_of`, N in 10–30, a finished
session carries its whole result. Composite keys keep a lineage on one
owner and page (`exam_questions_root_fk`) and a replaced question in the
same lineage (`exam_questions_variant_of_fk`); both are NO ACTION, so a root
with variants or a replaced question cannot be deleted (questions are
retired), while deleting the page or the owner removes the whole lineage.
`exam_answers` is keyed by `(session_id, question_id)`, unique on
`(session_id, root_id)`, and `(question_id, root_id)` must be a question and
its own root (`exam_answers_question_root_fk`, cascade).

Ports (`ExamQuestionRepository`, `ExamSessionRepository`,
`ExamAnswerRepository`, `ExamPageStateRepository`) are owner-scoped.
`listLineage` includes retired questions (what `newVariant` compares
against); `listActiveByPage` excludes them. `saveMany` writes a batch of
answers or none, and refuses a session or question that is not the owner's,
a question off the session's page or a root that is not the question's.
`ExamPageStateRepository.upsert` writes nothing for a page that is not the
owner's (it inserts from `pages` in the same statement). `createDrizzleExamRepositories(db)` builds all four on one
executor; `db` may be an open transaction, so exam writes join the caller's
commit together with study-engine's repositories. One shared contract
(`application/testing/exam-repositories.contract.ts`) runs against the fakes
(`pnpm test`) and the Drizzle adapters (`pnpm test:db`).

`domain/` imports only `src/shared/kernel` (`domain-is-pure`). The module
